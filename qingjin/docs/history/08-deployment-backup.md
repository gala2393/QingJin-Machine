# 部署架构、备份与运维

## 服务分工

| 服务 | 职责 |
| --- | --- |
| PostgreSQL | 持久化业务、账号、快照、审计及统计 |
| API | 业务接口、媒体处理、预览及静态站构建 |
| backup | 数据库和上传图片的定时、手动备份 |
| Nginx | 正式站、后台、图片资源与 API 代理 |

Compose 用命名构建上下文把展示站源码纳入 API 镜像；后台挂载本地构建结果。模板变化需重建 API 镜像再发布，后台变化需更新后台构建。推送 GitHub 本身不会自动完成部署。

## 初始化与运行

准备真实环境配置，构建后台，启动 Compose，执行迁移、首次导入、创建管理员及首次发布。镜像使用 Node.js 24，API 以非 root 用户运行，写入目录需匹配权限。

请求入口包括 /、/admin/、/api/ 和 /uploads/；预览使用独立主机名。Cloudflare 与 Nginx 的可信代理跳数应匹配实际链路，不能直接照搬其他环境。数据库、上传、发布与备份分卷保存。

## 备份流程

1. 默认北京时间每天 03:30 执行，默认保留 14 份，可配置。
2. pg_dump 压缩保存数据库，tar 归档上传图片，文件分别按 db 和 uploads 命名。
3. 先写临时文件，成功后改名；数据库和图片分别记录成功失败并清理历史文件。
4. 后台写入 .request，脚本轮询并转为 .running；请求排队不等于备份完成。
5. 后台列出匹配命名规则的备份文件与日志，并提供下载；未配置可用目录时显示未启用。

## 恢复边界

备份恢复、网站回滚和 Git 回退是不同操作。数据库恢复会影响当前业务状态，需要独立计划和确认。同机备份不能抵御整机故障，应保存异地副本。

数据库与图片分别生成，不应未经演练就视为严格同时刻的一致快照。定期验证可解压、数据库可恢复、图片可引用，以及网站能重新发布。
